# Dawa-Muhafiz — Complete Project Blueprint

AI-Powered Medicine Safety, Verification & Rapid-Alert Assistant for Pakistan

Dawa-Muhafiz will be a web application that helps people in Pakistan check whether their medicine's details match official safety alerts, understand potential risks, and access clear safety guidance in Urdu and Sindhi.

The goal is to build a project that is useful in the real world, technically impressive for a hackathon, feasible to implement, and honest about what AI can and cannot verify.

One fundamental decision will guide the entire project:

We are not training a new AI model to decide whether a medicine is fake. We are building a specialized medicine-safety system using existing AI, official documents, a structured database, and a deterministic verification engine.

That distinction is what makes the project more than a simple AI chatbot.

## 1. Project overview

Smart Medicine Scanner

Users photograph a medicine carton, blister pack, bottle, or supported barcode. AI and OCR extract the available information.

Official Alert Verification

The system compares medicine names, batch numbers, manufacturers, and other available details against validated DRAP alerts.

Evidence-Based Safety Result

Users see matching alert details, the original source, the reason for the warning, and the appropriate next steps.

Urdu & Sindhi Assistance

The application explains technical findings in simple language and can read warnings aloud.

## 2. Complete feature list

We should divide features into three levels so we can finish a working project without getting overwhelmed.

### Phase 1 — Must-have features (MVP)

These are the features the first working version must include.

1\. Medicine image upload and scanning

- Upload an image from a device.
- Support taking a photo on a smartphone.
- Accept cartons, blister strips, and bottles.
- Allow a user to retake or replace a blurry image.

2\. AI medicine information extraction

Extract the medicine name, strength, dosage form, manufacturer, batch number, expiry date, and registration number when visible. Use an explicit "unknown" or "unreadable" state rather than inventing missing information.

3\. DRAP alert database

Import validated official Rapid Alerts and Recall Alerts. Store the source, publication date, product name, affected batch, alert category, and recommended action.

4\. Batch-level matching engine

Compare extracted information against official records. Require a reliable match before displaying a confirmed alert match, and show which fields matched.

5\. Safety result screen

Display one of these outcomes:

- Red: matching official safety alert found.
- Amber: possible discrepancy or insufficient information.
- No known alert found: no matching record in the available database.

The last result must never be presented as proof that the medicine is genuine.

6\. Evidence and source links

Display the original DRAP alert, its reference number, relevant affected-batch details, publication date, and source link. Users should be able to inspect the evidence.

7\. English, Urdu and Sindhi

Translate the safety explanation into the selected language. Use reviewed templates for important safety messages.

### Phase 2 — High-value features

Once Phase 1 works correctly, add these features.

- Barcode/DataMatrix scanning: Read supported product codes and compare their information with available records.
- Voice warnings: Read the safety result aloud in Urdu or Sindhi.
- Manual medicine search: Search by brand name, manufacturer, batch number, or alert number.
- Packaging discrepancy flags: Highlight inconsistent text, missing information, or potentially suspicious packaging characteristics. These are investigation clues, not proof of counterfeiting.
- Report preparation: Generate a report with the scan details and relevant evidence that the user can review before submitting it through an official channel.
- Recent scan history: Allow users to revisit results if they opt in.
- Responsive PWA: Make the website easy to access from a mobile home screen.

### Phase 3 — Advanced features

These are future improvements, not requirements for the first hackathon version.

- Authorized integration with an official pharmaceutical verification service.
- Automated monitoring for newly published DRAP alerts.
- A document-processing pipeline for new PDF alerts.
- A pharmacist or administrator review dashboard.
- Improved extraction using a labelled medicine-packaging dataset.
- Offline access to a limited, clearly dated alert database.
- Aggregate analytics on common alert categories without exposing personal information.

Priority rule: Do not build every feature at once. A working scanner, correct alert matching, and clear evidence are more valuable than ten incomplete AI features.

## 3. The exact user workflow

This is the main journey the development team should implement.

1\. Open Dawa-Muhafiz

Choose a language and select Scan Medicine.

2\. Capture or upload a photograph

Validate file type, size and image quality.

3\. Extract medicine details

Vision model, OCR and barcode decoding where supported.

4\. Confirm extracted information

Let the user correct uncertain medicine names or batch numbers.

5\. Search official records

Compare the product and batch against validated alert data.

6\. Display the result

Show the finding, source evidence, limitations, and recommended next steps.

### Example result

A user scans a medicine whose batch number is `YT9D`.

The system extracts the name and batch number, finds a corresponding entry in its validated DRAP alert database, and displays the matching official document.

The result should explain that the batch matches the alert and show the relevant evidence. It should not independently diagnose the medicine or make a claim beyond what the official record supports.

If the image is blurry, the system should request another photograph. If no matching alert exists, it should state that no match was found in the available database.

## 6. Database requirements

We should organize the database so that every result can be traced back to its source.

The following is a proposed initial schema, not a claim about DRAP's own internal database.

| Table              | Important fields                                                                                    | Purpose                                                                  |
| ------------------ | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `alerts`           | `id`, `alert_number`, `alert_type`, `published_at`, `source_url`, `source_text`, `last_verified_at` | Stores validated official alert records.                                 |
| `affected_batches` | `id`, `alert_id`, `product_name`, `manufacturer`, `batch_number`, `strength`, `dosage_form`         | Stores individual products and batches mentioned in alerts.              |
| `products`         | `id`, `product_name`, `generic_name`, `manufacturer`, `registration_number`                         | Stores product reference information when available.                     |
| `scans`            | `id`, `created_at`, `extracted_fields`, `match_status`, `alert_id`                                  | Optional scan history, only where justified and appropriately protected. |
| `data_imports`     | `id`, `source_url`, `imported_at`, `review_status`, `error_details`                                 | Tracks document imports and data quality.                                |

The `affected_batches` table should reference `alerts` so that the application can retrieve the exact official document supporting a match.

Batch numbers should be stored as text, not numeric values, because they may contain letters, leading zeros, or other characters.

The system should also preserve the original spelling and a normalized search value where useful. Normalization can help find candidates, but must not silently convert an uncertain match into a confirmed one.

### How the database gets populated

1. Download a DRAP alert or recall document.
2. Extract its text and tables.
3. Review the medicine names and affected batches against the source.
4. Save the validated records.
5. Store the original source URL and publication date.
6. Periodically check whether the source has been updated.

DRAP's public website provides a dedicated recalls and rapid-alert section, and its alerts include affected product and batch details.&#x20;

## 7. Verification logic and result rules

This is the most important technical component of Dawa-Muhafiz.

We should define the rules before asking an AI agent to implement them.

| Situation                                                             | System result                   | Required behavior                                                                                       |
| --------------------------------------------------------------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Product and batch reliably match an official spurious/falsified alert | Red — Official alert match      | Show the exact alert, affected batch, source and safety guidance.                                       |
| Product and batch match an official recall                            | Red or prominent recall warning | Show the recall category and official recommended action.                                               |
| Some details conflict with available reference records                | Amber — Verification required   | Show the discrepancy and request a clearer photo or further checking.                                   |
| Batch number is missing or unreadable                                 | Incomplete scan                 | Ask the user to enter it or upload a clearer image.                                                     |
| No matching alert is found                                            | No known alert found            | Explain that the available database contains no matching alert; do not certify the medicine as genuine. |
| Multiple possible matches exist                                       | Ambiguous result                | Display possible records and request confirmation instead of guessing.                                  |
| Database or AI service is unavailable                                 | Verification unavailable        | Explain the failure and do not return a false green result.                                             |

A recall warning and a counterfeit warning should not be treated as interchangeable. The system must preserve the classification stated by the official source.

### Recommended matching algorithm

1. Extract candidate medicine names, batch numbers and manufacturer details.
2. Validate that the fields have plausible formats.
3. Find candidate records using normalized names and identifiers.
4. Require a matching batch number and sufficient product identity for a confirmed affected-batch match.
5. Check for ambiguity or conflicting information.
6. Return the relevant official source and exact matching fields.
7. If the evidence is incomplete, ask the user for more information.

Do not let a generative AI model independently choose the final safety status. Use deterministic rules to make the decision and AI to assist with extraction and explanation.

## 8. AI requirements and prompts

We should use the AI for a narrowly defined job: reading medicine packaging.

For example, the vision model should return a structured record containing:

```

{
  "medicine_name": "Augmentin",
  "strength": "625 mg",
  "dosage_form": "tablet",
  "manufacturer": "As printed on package",
  "batch_number": "YT9D",
  "expiry_date": null,
  "registration_number": null,
  "unreadable_fields": ["expiry_date"],
  "requires_user_confirmation": true
}

```

This is an illustrative extraction example, not a verified result for a particular physical medicine pack.

The AI prompt should instruct the model to:

- Extract only information visible in the image.
- Preserve batch numbers exactly as printed.
- Never invent missing details.
- Return `null` for unreadable or absent fields.
- Distinguish printed text from its own interpretation.
- Flag ambiguity and request a clearer photograph when necessary.
- Return data in the required JSON schema.

Gemini supports image input and schema-constrained structured output, making it suitable for this extraction stage.&#x20;

## 10. Security, privacy and medical safety requirements

These requirements are essential because the application deals with healthcare information.

- Do not store uploaded photographs longer than necessary unless the user explicitly opts in.
- Validate file types, sizes, and image content on the backend.
- Keep AI credentials and database secrets out of the frontend and source repository.
- Restrict administrative access to alert imports and corrections.
- Protect scan history using appropriate access controls.
- Avoid collecting patients' names, prescriptions, or other personal health information unless necessary.
- Do not provide diagnoses, recommend medicine substitutions, or advise users to change their prescribed treatment.
- Do not call a product genuine simply because no alert matches.
- Show source dates and disclose that the database may not include every current alert.
- Provide appropriate guidance to contact a pharmacist or healthcare professional when uncertain.
- Ask users to seek prompt professional advice if they have used a product identified in an official alert and are concerned about possible harm.

The result screen should clearly distinguish a documented regulatory finding from a visual anomaly or an inconclusive scan.

## 11. Testing and acceptance criteria

A feature is not finished simply because it works once on the developer's laptop.

For the first release, define testable acceptance criteria.

| Area           | Acceptance criterion                                                                                |
| -------------- | --------------------------------------------------------------------------------------------------- |
| Upload         | Supported images upload successfully; unsupported files receive a clear error.                      |
| Extraction     | The system returns structured fields and identifies unreadable values rather than fabricating them. |
| Verification   | A known affected batch matches the correct alert in the test dataset.                               |
| Batch accuracy | Similar batch numbers do not trigger an incorrect confirmed match.                                  |
| Evidence       | Every confirmed alert match links to its supporting official source.                                |
| Uncertainty    | Missing, conflicting, or ambiguous data produces an inconclusive result.                            |
| Localization   | Core warnings display correctly in English, Urdu and Sindhi.                                        |
| Security       | API keys are not exposed to the browser or committed to GitHub.                                     |
| Reliability    | API failures and database errors produce safe error states rather than fabricated results.          |
| Mobile         | The primary scan and results flow works on a smartphone-sized screen.                               |

Track batch-number extraction accuracy, exact-match precision, false positive rate, false negative rate, and the percentage of scans where the system correctly abstains.

For a safety-oriented application, avoid optimizing only for the number of scans that produce a confident result.

## 13. Development roadmap for your coding agents

Since you plan to use AI coding agents, give them one well-defined phase at a time.

Phase 1

Foundation

Requirements and architecture

Finalize scope, repository structure, data schema, API contracts, UI flow, and safety rules. Do not begin by generating the entire application in one step.

Phase 2

Frontend

Build the complete interface

Implement the home page, scanner, extraction confirmation, result states, alert details, responsive layout, and language selector using mock data initially.

Phase 3

Data

Build the official alert database

Collect and validate a sample of DRAP records, create database tables, import the records, and test batch matching independently of AI.

Phase 4

AI

Integrate image extraction

Connect the backend to Gemini, implement structured extraction, validate the response, and handle blurry images and missing fields.

Phase 5

Integration

Connect the full workflow

Wire the scanner to extraction, extraction to verification, and verification to the evidence-based results page.

Phase 6

Quality

Test, secure and deploy

Run positive and negative test cases, fix defects, verify secrets and permissions, deploy the application, and rehearse the demo.

Use GitHub branches and small commits for each phase. Require the agent to run the relevant tests and summarize changed files, known issues, and remaining work before moving to the next phase.

## 14. How to make Dawa-Muhafiz stand out in the hackathon

The project should demonstrate more than an AI-generated answer.

Focus your live demonstration on five things:

1. A real official alert: Use a verified DRAP document as the source of truth.
2. A medicine photo: Show the application extracting the batch number.
3. A correct database match: Demonstrate that the batch matches the exact official record.
4. An explainable result: Display the original source and explain the warning in Urdu or Sindhi.
5. A safe negative case: Scan a product with no matching alert and show that the application does not claim it is genuine.

That last case is particularly valuable because it demonstrates that you understand the limitations of AI in a safety-critical setting.

## 15. Final project scope

For the first release, I recommend committing to this exact scope:

## Dawa-Muhafiz MVP

The minimum complete version worth presenting.

Responsive React web application

Medicine photo upload and camera capture

Gemini-powered medicine information extraction

Validated DRAP alert and recall database

Batch-level deterministic matching

Red, amber and no-known-alert outcomes

Original official alert links and evidence

English, Urdu and Sindhi safety explanations

Clear uncertainty and error handling

Automated tests for matching and extraction

Live deployment and a documented demo

Leave automated web crawling, advanced counterfeit-image classification, user accounts, voice features, extensive analytics, and pharmaceutical authentication integrations for later unless the core product is already working.

### What the team should do first

Before coding, collect a small set of official DRAP alerts and build the structured database. In parallel, finalize the user interface and project architecture.

Then make the database matching work independently. After that, integrate AI-based image extraction.

This order is important: the database provides the evidence, AI extracts the details, and the verification engine connects the two.

That is the foundation of a useful Dawa-Muhafiz project—not simply another chatbot that guesses whether a medicine is fake.
